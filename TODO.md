- **#48 Compile the instructions on the SERVER (option, ☁/⚡ toggle)** — ONLY the graph→TF **compilation** runs server-side. On a STRUCTURAL change (#46 trigger rule) the client sends the graph → `/api/tf/compile` → the server runs the lightweight TRANSLATOR (plain logic) → returns the compiled TF instruction recipe (`build(params)`). The **CLIENT executes** that recipe in its own TF, and PARAM changes are evaluated client-side → real-time preserved. The server does NOT run TrueForm (no execution, no 29 MB WASM, no mesh built server-side). Benefit = **thin concealment**: the translator/recipe-generation logic stays server-side (never shipped); the value scales with part complexity — a complex assembly's recipe is inconvenient to reconstruct, a trivial part isn't worth protecting. Toggle vs #46's client-side compile like Manifold's ⚡/☁.
- **#49 Server-compile OUTPUT = WASM/WAT instead of JS (another option)** — same server-compile flow as #48 (structural-change trigger, client still executes + evals params real-time), but the server emits a **WASM/WAT module** for `build(params)` instead of a readable JS recipe. Thicker concealment than #48's JS (binary vs readable), at the cost of a server-side WAT/AssemblyScript emitter. The client runs the WASM (still runs TF client-side). This realizes the earlier #47 idea as a concrete OUTPUT-FORMAT option alongside #48. Honest caveat (unchanged): WASM is decompilable (`wasm2wat`) and the `tf.*` calls/params + the output mesh stay observable → **mild, not strong** concealment; value still scales with part complexity. NOTE: this is server-side compilation-to-WASM only — NOT server-side execution.
- **#47 (FUTURE / optional hardening) Server-compile the part → WASM `build(params)` for concealment** — the OPTIONAL second tier on top of #46: on a STRUCTURE change, the server compiles the part into a WASM whose exported `build(p1,p2,…)` takes the params as args (via a WAT/AssemblyScript emitter); param changes then call it client-side (real-time). Adds NO speed over #46's JS path (TF does the geometry either way) — its ONLY benefit is MILD concealment of the parametric recipe. Do this ONLY if protecting the recipe becomes a real, prioritized need; it must NOT gate the #46 real-time work. Real concealment = server-side render (send mesh only), which forfeits the client-side speed — same speed↔concealment tradeoff. Also per-part WASM compilation is heavy vs a JSON recipe + one generic client runtime. Worth a doc: what it does/doesn't protect, a generic-WASM-interpreter-over-encoded-blob option, and when server-side is the real answer. Ties #46/#44.
