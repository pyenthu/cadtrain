REAL-TIME (near-term, JS — build this FIRST): TWO-TIER, all client-side, no server + no WASM. STRUCTURE change (add part/param) → re-translate the graph into a JS `build(params)` fn (µs).   **TRIGGER RULE (the linchpin):** (re)compile ONLY on a STRUCTURAL change — add/remove/rename a part or param, rewire, change an op/primitive. A pure VALUE change must NEVER trigger a (re)compile. Detect via a **structural signature/hash** that INCLUDES topology (nodes, ops, wiring, param names + count) and EXCLUDES param VALUES — mirrors the existing `scriptHash`/bake-cache keying. Same structure-hash ⇒ skip compile, just `build(newParams)`. This is exactly what keeps param edits real-time AND makes the server compile (#48) rare (only on structure change, not per keystroke).
- **#48 Server-compile OPTION (☁/⚡ toggle) — thin concealment, real-time preserved** — offer graph→TF compile server-side (`/api/tf/compile`) as an alternative to #46's client compile, toggled like Manifold's ⚡client/☁server. The graph→TF TRANSLATOR stays server-side (never shipped → thin concealment of the compiler logic); the server returns the compiled PARAMETRIC instructions (`build(params)` recipe) and the client still evals PARAM changes locally → real-time preserved (only the one-time STRUCTURAL compile is a server call). TF also runs headless in Node (no cross-origin isolation server-side — proven via the bun decode-probes), so this doubles as the server half of the TF matrix + a headless CI test hook. Concealment ladder: client-JS (none) → server-compile-returns-instructions (THIN, this) → server→WASM #47 (mild) → server-execute/mesh-only (full, forfeits client speed). KEY: the thin-concealment value SCALES WITH COMPLEXITY — a trivial part is copyable regardless (measure the mesh), but a COMPLEX assembly's compiled recipe (many ops / nested params / chained unions+lathes) is genuinely inconvenient to reconstruct → server-compile earns its keep precisely on the complex/valuable parts, and doesn't bother protecting the simple ones (which can't be protected anyway). Cache the ~29MB TF WASM as a server singleton. Rides #46.
- **#47 (FUTURE / optional hardening) Server-compile the part → WASM `build(params)` for concealment** — the OPTIONAL second tier on top of #46: on a STRUCTURE change, the server compiles the part into a WASM whose exported `build(p1,p2,…)` takes the params as args (via a WAT/AssemblyScript emitter); param changes then call it client-side (real-time). Adds NO speed over #46's JS path (TF does the geometry either way) — its ONLY benefit is MILD concealment of the parametric recipe. Do this ONLY if protecting the recipe becomes a real, prioritized need; it must NOT gate the #46 real-time work. HONEST caveat to validate: WASM is only MILD obfuscation — `wasm2wat` decompiles it and the imported `tf.*` calls + numeric params stay visible; the rendered mesh itself reveals the shape (measurable). Real concealment = server-side render (send mesh only), which forfeits the client-side speed — same speed↔concealment tradeoff. Also per-part WASM compilation is heavy vs a JSON recipe + one generic client runtime. Worth a doc: what it does/doesn't protect, a generic-WASM-interpreter-over-encoded-blob option, and when server-side is the real answer. Ties #46/#44.
