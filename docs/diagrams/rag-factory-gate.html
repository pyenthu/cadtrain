cadtrain · #49 · rag factory

The gate was measuring the dice,
not the corpus.

The factory generates RAG atoms, then asks: did they make the model better? On 3 Aug it answered no and threw the atoms away. That answer was noise. Here's what the loop does, the two bugs in how it judged, and the fix now in place.

the loop

What the factory is trying to do

The local model (qwen2.5:1.5b) builds apps badly. The bet is that giving it better retrieval examples — atoms — makes it build better. The factory tests that bet empirically, entirely locally, at zero token cost.

01 · MEASURE

Score the model on partsdash + opsdash with the current corpus. This is before.

→
02 · FILL

Ollama generates a few new dashboard apps, deduped against existing goldens, split into atoms.

→
03 · MEASURE

Score again with the atoms added to the trial corpus. This is after.

→
04 · GATE

Did after beat before? Promote the atoms, or discard them. This step was broken.

Everything writes to runs/trial-corpus/ — the shared prod volume is never touched until a result clears the gate.

the problem, in one picture

The model scores differently every time you ask it the same question

Measured on identical corpora, the same eval returns a different number each run. So a single before-score and a single after-score can differ by several points with no change at all. The question is never "did the number move" — it's "did it move more than it moves on its own."

Case A — what actually happened on 3 Aug
One run before, one run after. No σ. The gate called it a regression.

But those two numbers were already known to be the same thing.

Earlier that morning the hill-climb ran opsdash twice on an unchanged corpus and got 48.0% and 41.1% — the exact pair the factory later read as a 6.9-point regression. Same for partsdash: 42.3% and 38.1%. The factory measured the spread of the dice and attributed it to the atoms.

the fix

Widen the band to fit the noise, then judge

Run each measurement three times so it carries its own σ. Set a band around before of max(3pp, 2 × pooled σ). Only a delta that escapes the band counts. Crucially this adds a third verdict — the honest one.

A 5-point drop — well past the old fixed 3pp tolerance, so the old gate would have called it a regression. But these runs scatter by ±4.9 on their own, so 5 points means nothing. This is the case that matters: the band has to be derived from the data, not fixed in advance.

bug two

The gate never looked at the numbers it printed

Separate from the noise problem: the old gate called eval-app-build --gate, which runs the whole eval again. So the score it judged was a third, unrelated sample — and the "after" figure shown in the log had no bearing on the verdict.

OLD — three separate dice rolls

  • run eval → sample #1 → write factory-baseline.json
  • gap-fill: add atoms
  • run eval → sample #2 → log "after 41.1%"
  • run eval AGAIN → sample #3 → compare #3 vs #1
  • verdict describes a number never shown to you
  • …and does it twice for APPS_A[0] (duplicated call)

NEW — judge what you measured

  • run eval ×3 → before: mean + σ
  • gap-fill: add atoms
  • run eval ×3 → after: mean + σ
  • parse both existing outputs — no new run
  • band = max(3pp, 2 × pooled σ) → WIN / REGRESSION / INCONCLUSIVE
  • verdict cites the exact numbers in the log

Removing the redundant re-runs also makes the gate step free — it's now arithmetic on files that already exist, where before it cost three extra full evals per app.

reference

Four verdicts, and what each one means for the atoms

VerdictConditionWhat happens to the atoms
win Δ > +band Real improvement. Promote from trial-corpus/ to the prod volume.
regression Δ < −band Real harm. Discard, and look at what the generator produced.
inconclusive |Δ| ≤ band New. The experiment didn't resolve. Keep quarantined and raise RUNS — don't throw good atoms away on a coin flip.
nogate n < 2 Single sample carries no σ. Refuses to judge at all — this is what the 3 Aug data now returns.
