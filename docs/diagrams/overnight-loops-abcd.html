How the guard changes one iteration

claude --print→ guard_blocked?→ guard_backoff→ sleep toward reset→ retry same item

└─ or, on the Nth consecutive block: abort the loop entirely

guard_blocked "$out"

True when the output is empty, a session/weekly/rate limit, a transport error (ENOTFOUND), or expired auth — rather than real work.

guard_backoff "$out"

Parses "resets 9:30pm" out of the refusal and sleeps toward it, capped at GUARD_MAX_SLEEP. With no parseable time, backs off 1 → 2 → 4 → 8 → 16 min.

abort

After GUARD_MAX_FAILS consecutive blocks (default 5) the loop stops and logs why. Slept through the reset five times means something else is wrong.

guard_ok

Clears the consecutive-failure counter on any real response, so a single transient blip can't accumulate toward the abort.

The second half of the fix: don't advance the index

  f="${FILES[$(( i % ${#FILES[@]} ))]}"; i=$((i+1))
  f="${FILES[$(( i % ${#FILES[@]} ))]}"
  out=$( ... | claude --print 2>/dev/null)
  if guard_blocked "$out"; then guard_backoff "$out" || break; continue; fi
  guard_ok; i=$((i+1))
  # Advancing i on a block would let the limit window silently skip files,
  # which is how a "full pass" reported 2,664 files over a set of 72.

verified with fakes — no API calls

Detection: session limit ✓ · weekly limit ✓ · API Error … ENOTFOUND ✓ · empty ✓ · whitespace ✓ — while CLEAN, a real findings paragraph, and real JSON all pass through untouched. Reset parsing: 9:30pm → 50,563 s, 2:10am → 67,363 s, unparseable → exponential. Abort fired on the 4th consecutive block with GUARD_MAX_FAILS=4, and guard_ok reset the counter to zero.
