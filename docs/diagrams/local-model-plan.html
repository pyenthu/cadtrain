Five test apps. The score measures how close the built app is to a known-good version — panel types, nesting, variables, theme, title. Claude averages about 92%. The local model averages about 46%. That 46-point gap is the thing we're trying to close.

02

The idea: don't retrain it — show it better examples

What we are not doing

We're not fine-tuning the model or training new weights. That's slow, expensive, and has to be redone every time the app format changes.

What we are doing

Every time the model builds something, we first hand it a few worked examples to look at. Better examples produce better output — immediately, with no training.

So the real product isn't the model. It's the library of examples — and a machine that keeps making that library better.

In your words from the project notes: a self-improving RAG DB so the local small model gets better — better function definitions, better semantics.

The nice property: it compounds. A good build can become tomorrow's example. The library gets better, which makes builds better, which makes better examples. That's the flywheel.

03

The method: a factory that only keeps what works

Adding examples doesn't automatically help — some make things worse. So every batch has to earn its place by measurement. One turn of the loop:

Judge honestly — the gate

Did it really get better? Keep if yes, throw away if worse, and say "don't know" if the change is too small to tell apart from random variation. That third answer is the one we just added.

now free — reads existing results
repeat — each turn should leave the library a little better

Why step 5 needed fixing. The small model gives a different score every time you run it, even with nothing changed — swings of 5 to 20 points. The old gate ran the test once before and once after, so it was reading that randomness as if it were progress or damage.

On 3 August it threw away a batch of examples for "making things worse." Those exact numbers — 48.0 then 41.1 — had been recorded that same morning from two runs with no change at all. It was measuring the dice.

Fix: run each measurement three times, and only believe a change bigger than the model's own random wobble. Otherwise report "don't know" instead of guessing.

04

What success looks like

near term

Every gain is real

The score only moves when something genuinely improved. No more throwing away good work because of a bad roll, or keeping bad work because of a lucky one.

middle

The library improves itself

The loop runs unattended overnight, costs nothing, and each morning the library is measurably better than the night before.

the goal

Ship without the cloud

The local model builds apps well enough to be the product's real engine — so nothing a user types ever leaves their machine.
